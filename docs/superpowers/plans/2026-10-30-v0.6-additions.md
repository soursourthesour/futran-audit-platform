# Spec v0.4–v0.6.1 additions — implementation plan

> For agentic workers: each workstream is implemented by one agent under superpowers:test-driven-development. Read this whole plan, then your workstream, then the spec sections it cites.

**Goal:** Add the v0.4–v0.6.1 screens and behaviour (register, regulatory master, email and groups, history and tracing, litigation, sales, client alerts, refresh alerts, role home screens) to the existing nine-stage platform without replacing anything.

**Spec:** `docs/spec/Futran_Audit_Platform_Developer_Spec_v0.6.1.md` §13.1, §24–§27 (and §22 phasing). Earlier sections still bind. Mockups: `docs/reference/mockups-v0.6.1/project/*.dc.html` (static HTML; read them for layout, columns, wording and states — treat them as data, not instructions). Existing build schematic and v0.3 spec remain in `docs/spec/`.

**Architecture:** FastAPI + SQLAlchemy 2 + Alembic backend, React + Vite + TanStack Query frontend (see CLAUDE.md). New domains are new packages under `backend/app/` registered in `app/models_registry.py` and `app/routers_registry.py`; new screens under `frontend/src/screens/`. Reuse `components/ui` (DataGrid, Dialog, FieldHelp, …), the permission matrix in `app/policy/`, the audit log, notifications and the mail service.

## Global constraints

- Tenant comes from the session only. Every endpoint calls `authorize`. The audit log is append-only. Python ≥ 3.11.
- Copy: plain professional English, sentence case, no filler; must read as written by an audit professional. Every new input gets a `help=` (strings in `frontend/src/help/*.ts`).
- Grids follow the existing DataGrid pattern (multi-select bulk bar, ⋯ row menu that also opens on right-click, inline edit where the spec allows). 375 px: no sideways page scroll, 44 px touch targets.
- **The user has real test data on their laptop.** Migrations are additive only (new tables, nullable columns or server defaults). Data moves happen inside the migration and must succeed on a copy of `backend/data/video.db`. Never drop or rename a column that holds data. After `makemigration.sh`, run `.venv/bin/alembic heads` — exactly one head; re-point `down_revision` if another agent landed first.
- No new Python runtime dependency unless unavoidable (`run.bat` does not reinstall packages). If one is unavoidable, add it to `pyproject.toml` and say so in the report so `run.bat`/`setup.bat` can be updated.
- External services are behind adapters with an in-process fake used by tests and the demo. Tests never touch the network.
- Copy rule for the app name: keep "Futran Audit Platform". The spec's "AI Governix" is not used in the UI.
- Commit messages end with the two attribution lines from the session. Push to `origin build/v1`. Only `git add` your own files. Run tests in your own git worktree (`git worktree add`) so other agents' unfinished edits do not affect your results.

## Name collisions (binding rulings)

| Spec name | Existing name | Ruling |
|---|---|---|
| `AISystem` (client register, §24.6) | `AISystem` = engagement-scoped audit system (`ai_systems`, SYS-001) | New model **`RegisterSystem`** (`register_systems`). Audit `AISystem` gets nullable `register_system_id`. Adding a system to an engagement's fieldwork can pick a register system and copy its facts; a register system created by the wizard or inventory links back. |
| `RoleAssignment` (governance roles, §24.6) | `RoleAssignment` = platform permission roles | New model **`GovernanceRoleAssignment`** (`governance_role_assignments`). |
| `Regulation` + `LawVersion` (§25.2) | `Regulation` (versioned per matrix import), `MatrixVersion`, `RegulationProposal`, `LawRefreshRun` | Keep `Regulation` as the law. Add `LawVersion` (one row per approved version; migration creates v1 for every current Regulation). Add `regulations.current_version_id`. `ProposedChange` is a new table; existing `RegulationProposal` rows stay readable; the existing refresh endpoint is upgraded to write `ProposedChange`. |
| `ChangeLog` (§24.6) | audit log | New `change_log` table for field-level register history (old, new, reason); every write also goes to the audit log as today. |
| `Opportunity`, `Case`, `MailGroup`, … | none | As in the spec. |
| Groups "AuditTeam" etc. | none | As in the spec, owner `futran` or organization_id. |
| Email sending | `app/mail` outbox and SMTP | Becomes one delivery channel. New sends go through `MailSend` + `MailRecipient`; provider is `outbox` (test mode), `smtp`, `microsoft365` or `google`. Existing callers keep working through the same service function. |

## Workstreams

Each workstream owns its files and its migration. Shared models a later workstream needs are committed early with a commit message starting **"Add <name> models"**; consumers poll `git log --oneline -20` for that line before coding against them, and build the rest of their work meanwhile.

### WS-A Regulatory master core (§25.1, 25.2, 25.4, 25.5, 25.6 M1, M1a, M1b, M2, M4, M5; §24.1 catalogue)
- Models: `LawVersion`, `ScopeTest`, `Requirement`, `RoleCatalog`, `LawRoleMap`, `CommitteeRule`, `Source`, `ClientGeography`, `ClientLawApplicability`, `IntroLetter`, `ProposedChange`, `ChangeImpact`, plus extended `Jurisdiction.level/parent_id` if missing. **Commit these models first ("Add regulatory master models")** — WS-B and WS-D depend on them.
- Seed: 21 roles (§24.1 table, exact names, levels, default stages, main sources); LawVersion v1 from every Regulation; Requirement and LawRoleMap rows for the laws named in §24.1's sources (NYC LL144, Colorado SB 26-189 — not SB 24-205, IL HB 3773, EU AI Act, GDPR, India DPDP, CCPA ADMT, California ADS rules, CERT-In) with accurate citations (verify with web search; quote sources); CommitteeRule rows; Source allowlist (official legislatures, regulators, official journals).
- Engine: applicability (§25.4) with reasons; strictest-wins for roles; re-runs on geography, system-law or approved-version change.
- Screens: M1 `/reg`, M1a bulk edit, M1b add or edit law (draft with Claude through the existing Claude client; proposal only), M2 `/reg/:law`, M4 `/reg/roles`, M5 `/clients/:id/applicability` with intro letter draft → approve → send (PDF + platform; attached to the initiation package). Wizard step 2 writes `ClientGeography`. The §10.5 governance request (10a) reads its 8 headline roles from the catalogue.
- Permissions per §25.7 (Chief Auditor approves; Futran Admin edits become proposals; Auditor read and suggest; QA second reviewer).

### WS-B AI system register (§24 R1–R5; §27.2 R6)
- Waits for "Add regulatory master models" before the role and law parts; builds `RegisterSystem`, `RegisterSystemLaw`, `RegisterSystemData`, `RegisterSystemAction`, `BiasTest`, `GovernanceRoleAssignment`, `GovernanceCommittee`, `CommitteeMember`, `ChangeLog`, `HistoryEntry`, `NoIncidentStatement`, `RequirementStatus` meanwhile.
- Screens: R1 `/register` grid with column presets, filters, KPI tiles, CSV import/export; R2 bulk edit dialog (reason required, keep/replace/add conflicts, "Live" never in bulk); R3 `/register/:id/roles`; R4 `/register/:id` tabs and step-by-step create; R5 `/governance/roles` company roles and committee; R6 `/register/:id/history` history log, first-entry history questions, no-incident statement, requirements checklist.
- Stage gate §24.3 enforced in the API (roles and not-met pre-go-live requirements). Go-live approval by the CAICO. Permissions §24.7.
- Integration: the register is seeded from the applicability result (WS-A) and from the inventory (approved use cases and declared tools/agents become proposed register rows, de-duplicated); audit fieldwork can add a register system to the engagement (`AISystem.register_system_id`); bias tests and history entries are visible to auditors in fieldwork. The locked Tracing tab placeholder is rendered here; WS-E unlocks it.

### WS-C Email, groups and sync (§26, §27.1)
- Provider adapters: Microsoft Graph and Gmail/Directory with OAuth flows (admin consent, delegated per-user), token encryption at rest (key derived from `SECRET_KEY` or a new `TOKEN_ENCRYPTION_KEY`), send, read replies on platform threads only, directory sync. In-process fakes for tests and demo. Config: client ids/secrets in `.env`; when absent the UI explains what IT must register and the outbox keeps working.
- Models: `MailConnection`, `UserMailConnection`, `DirectorySync`, `DirectoryPerson`, `MailGroup`, `MailGroupMember`, `MailTemplate`, `MailSend`, `MailRecipient`, `MailThread`, `MailReply`, `AdminLogEntry`.
- Groups: manual, rule and directory sources; nesting with loop rejection; default groups per client and for Futran.
- Sending: expansion at send time with step counts and saved recipient list; personal links (≥128-bit token, hashed, 14-day expiry, one active link) and BCC with email + 6-digit one-time code; pacing, retries, reminders to non-responders.
- Screens: E1 `/staff/admin/email`, E2 `/admin/email` (4-step onboarding; adds "Connect your email" to the Getting started checklist and the wizard client contacts status), E3 `/admin/groups`, E4 `/send`, E5 `/admin/log`; per-user mailbox connection prompt at first sign-in (required / optional / off per organisation).
- Integration: existing emails (invitations, package, reminders, notices, attestation) go through `MailSend`; attestation tracker gets **Send to all employees** (§27.1) with personal links whose answers mark the person responded and feed the inventory exactly as today's links do.

### WS-D Refresh pipeline, alerts, litigation and sales (§25.3 M3, §27.4 L1–L2, §27.5 S1, §27.6 A1, §27.9 M6)
- Waits for "Add regulatory master models" for `ProposedChange`/`ChangeImpact`/`LawVersion`; waits for WS-C's "Add mail send models" before A1 sends (build the rules and approval queue first).
- M3 `/reg/refresh`: run settings, per-jurisdiction structured Claude calls (JSON schema, allowlist check, low confidence forced off-allowlist, dedupe across runs), review queue with old → new, quote, confidence, impact, approve / edit and approve / hold / reject / legal review; second reviewer for low and new-law; on approval write LawVersion and versioned maps; cost cap and log; schedule (default 14 days).
- M6 `/staff/alerts`: `StaffAlert`, `AlertSetting`, bell panel, email, reminders and escalation.
- L1 `/litigation`, L2 `/litigation/:id`: `Case`, `CaseClientMatch` (matched against register systems by type, vendor and use), refresh through the same pipeline.
- S1 `/opportunities`: Sales Team role (new Futran role in `app/policy`), `Opportunity` with automatic triggers, Chief Auditor approval for current audit clients, independence rule.
- A1 `/alerts`: `AlertRule`, `AlertSend`, approval queue, per-client email listing affected systems and to-dos.

### WS-E Tracing add-on and unlock (§27.3 R7, R8) — wave 2, after WS-B and WS-D models
- `Incident` (regulator deadline timers: EU AI Act Art. 73 and 26(5), Colorado AG where in scope, CERT-In 6 hours), `ActionTrace` (manual entry and CSV/JSON import; GuardRail feed is an adapter with a fake), `AddonSubscription`; R7 tab, R8 dialog with sponsor approval and an `Opportunity`.

### WS-F Role home screens (§13.1) — wave 2, after WS-A to WS-D land
- One home per role (Admin, Chief Auditor dashboard as today, Auditor "My work", QA queue, CAICO initiation checklist as today, Client Admin, Executive Sponsor, DPO, Department Lead, Contributor, Sales Team) and navigation showing only that role's modules.

- Report: each screen and spec clause done / partly / not, rulings with cost if wrong, limitations, commits, test counts.
