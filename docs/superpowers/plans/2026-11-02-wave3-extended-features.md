## Rules for every AI-powered feature (F1, F5, F10, F14) — binding

1. Output is a suggestion with status `suggested`. Nothing reaches a client, a finding, a score or a report until a named Futran user accepts it (for F10 the client's own reviewer accepts their answers). No auto-approve setting. "Accept all high-confidence" is allowed only as an explicit click by the user, and each acceptance is logged separately.
2. Every suggestion cites the document, page and passage it came from, plus `high`/`medium`/`low` confidence. The backend checks each quote is actually present in the extracted text of the cited document (normalised whitespace, case-insensitive); a quote that is not found makes the suggestion `unsupported`, and an unsupported suggestion cannot be accepted as an answer or as evidence.
3. Every call writes an `AIInteraction` (spec 21 schema) and an audit log entry; acceptance, edit and rejection update it (`decided_by`, `decided_at`, `reason`).
4. `Engagement.ai_features_enabled` (nullable bool, default false). The Chief Auditor turns it on per engagement, recording that the client consented in the engagement letter. When off, every AI control is hidden for that engagement and AI endpoints return 403.
5. Model calls go through a single adapter `app/ai/client.py` (WS-G) with an in-process fake (`AI_CLIENT=fake` in the browser tests and demo; injected factory in pytest). No web search in F1/F5/F10 — the model only reads the text the platform gives it. Use `output_config.format` JSON schema for structured replies (no citations feature in the same request; the backend does its own quote check per rule 2).
6. The platform's own AI features are registered as `RegisterSystem` rows in Futran's own organization (WS-L seeds them).

## Workstreams

### WS-G AI copilot and AI foundation (F1 core, F5, F10; screen 25)
- `app/ai`: adapter + fake (rule 5); text extraction from PDF (`pypdf`, keeping page numbers), DOCX (`python-docx`, paragraph-based "pages" of ~3,000 characters) and plain text; `AIInteraction`; quote check (rule 2); `Engagement.ai_features_enabled` with the Chief Auditor's switch on the client page and the consent note.
- Screen 25 on the system assessment (`/systems/:id/assess`, and the fieldwork view): "Copilot suggestions" panel for a section — document pre-fill from the engagement's uploaded evidence documents (answers proposed per template question with document, page, quote, confidence); Accept / Edit / Reject; Accept answer + create draft finding (draft goes to the existing findings flow as `draft`, never past QA); unsupported items offer "Add to interview list" and "Create evidence request" (existing document-request flow); "Accept all high-confidence (n)"; evidence check per checklist item; completeness review before sign-offs 5 and 7 (unanswered required questions, ticks without evidence, contradictions between interview answers and documents, answers missing a source person — the deterministic parts computed without AI, contradictions by AI with citations); "Ask the copilot" box answering from the engagement's documents with citations; AI interaction log page for the engagement (Chief Auditor, Lead Auditor, QA).
- Draft finding text (condition, criteria, cause, effect, recommendation) and summaries (system, engagement, client) for the Chief Auditor and the report executive summary — suggestions only.
- Client Q&A helper: on client question screens an "Explain this question" button that explains the question from the glossary and help text; it never suggests an answer (test the prompt and the fake for this).
- F5: on the law record (M2), "Extract obligations" proposes `Obligation` rows (actor, action, condition, deadline, citation, linked requirement and template question ids) from the law version's stored text and requirement passages; Legal Reviewer or Chief Auditor approves; approved obligations show on M2 and feed lineage (WS-K reads them).
- F10: client screen `/questionnaires` (Client Admin, CAICO): upload XLSX/DOCX/PDF customer questionnaire → detect questions → draft answers from the client's `AnswerLibraryItem`s, published policies (WS-I, if present) and the latest signed Futran report, each with citations; facts drawn from the signed report are marked "Audited by Futran"; client reviewer accepts/edits; export in the original format (XLSX: answers in the next column; DOCX: answer paragraph after each question; PDF: export as DOCX with a note). Approved answers grow the library.
- Permissions: Auditor, Lead Auditor, Chief Auditor use the copilot on their engagements; QA reads the log; clients never see Futran's copilot.

### WS-H Regulatory change alerts and impact assessment (F4, F8; screens 26, 28)

Approved law-library changes appear in the list read-only. Published updates that change a law's facts must go through M3 as a `ProposedChange` (button "Propose the law change"), so the law matrix version stays the single source.
- Client view `/updates` (CAICO, Client Admin, Department Lead read): "What this means for you" — published updates that match the client, with affected systems and to-dos, plus the client's deadline calendar.
- Weekly digest email to client CAICOs (scheduled job, claim-once pattern from `app/mail` to avoid double sends; off by default per client until the Chief Auditor enables it in settings).
- Screen 28 `/projects` and `/projects/new` (client): new AI project intake (purpose, tool or vendor, planned go-live, users located in, data it will use, decisions about people, talks to the public) → live proposed tier (reuse the §11 tiering rules used by the register/inventory) and laws matched (reuse the applicability engine's scope tests) → required assessment depth → reviewers (Department Compliance Lead, DPO, CAICO decides) → `approved` / `approved_with_conditions` / `rejected`; conditions tracked like commitments; "Ask Futran for an independent opinion" opens an S1 opportunity (Tier 3 only). On approval the project becomes a register system (stage `proposed`) or links an existing one.
- `ReassessmentTrigger` with `raise_trigger(...)` (commit early): types per spec; sources manual / monitor / regulatory_update / schedule; detected automatically on register edits (version, data type, jurisdiction, population, vendor), on published regulatory updates that match the system, and after 12 months; a trigger shows on the register record and the client home and reopens the affected assessment sections when the system is in an engagement.
- Register the monitoring check "Reassessment overdue".

### WS-I Policy builder, training and Trust Center (F7, F12, F9; screens 27, 32, 33)
- Screen 27: from a governance commitment of kind "Will create" (existing 10a/§10.5 flow), "Start from Futran template" → guided questions → generated draft (deterministic template rendering — no AI) → client edits (rich text limited to headings, paragraphs, lists) → "Send for approval" to the CAICO → publish → acknowledgment campaign reusing attestation (each employee acknowledges the policy) → the commitment closes with the published policy as evidence. - Screen 33 `/training` (AI literacy owner role holder, CAICO, Client Admin): five Futran modules (§21 F12) authored as structured content with short quizzes (`backend/app/training/modules/*.yaml`), assign by department, role or email group, completion and quiz score, target % and date, reminders through the mail service, completion certificate PDF, completion by department, "Export SCORM" (SCORM 1.2 zip built with `zipfile`); employee player `/learn/:assignment` and the token link variant for people without accounts (reuse the personal-link pattern from attestation). - Screen 32: client Trust Center editor `/trust` (CAICO edits, Client Admin views) and the public page `/trust/:slug` (no sign-in; optional NDA click-through gate before detailed documents; view counts by day). ### WS-K Bias calculator, heat map, lineage, benchmarking and carry-forward (F11, F13, F6, F15, F16; screens 29, 34, 35)
- Screen 29 `/systems/:id/bias-test` (Auditor, Lead Auditor; client CAICO may upload when the auditor asks): CSV upload (id, selected or score, sex, race/ethnicity, optional age band) with validation report; selection-rate method and scoring-rate method for scored tools exactly as the NYC DCWP rules define them (6 RCNY §5-301 — verify the definitions with web search and quote the rule in the module docstring: selection rate, impact ratio = category rate ÷ most-selected category rate, scoring rate = rate of scoring above the sample median, intersectional categories of sex × race/ethnicity, the option to exclude categories under 2% of the data from the impact-ratio calculation with the count still reported, and the unknown-category count); tabs race/ethnicity, sex, intersectional; 4/5ths flag; statistical parity difference and equal opportunity difference when outcome labels exist; thresholds from the risk methodology settings (0.80 and 2% defaults). "What this run feeds": 6.2.06 lowest ratio, 5.1a.03 unknown share → rating, draft findings (suggestions through the findings draft flow), LL144 public summary tables (`PublicSummary`), and "Record as bias test" on the linked register system (existing `BiasTest`). - Screen 35 `/clients/:id/heatmap` (Futran: Lead Auditor, Chief Auditor, QA): systems placed by inherent risk band (columns) × control maturity (rows) from existing scoring; cell colour = residual band; provisional scores marked *; knock-out note; findings view by severity × domain; filters by department, build type, framework; export to the report (PNG via a server-rendered SVG, included as a report appendix section). - Screen 34 `/insights` (Chief Auditor; Sales sees only the practice view without client names): anonymized peer comparison by domain, industry and size band; a figure is shown only when its peer group has ≥ 5 consenting clients (consent = a flag recorded from the engagement letter; add `Organization.benchmark_consent` nullable bool); never identify a client; practice view of most common findings → service offering; `BenchmarkSnapshot` recomputed on report sign-off.
