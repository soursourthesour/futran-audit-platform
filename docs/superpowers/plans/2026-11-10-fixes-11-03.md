**Source:** `docs/changes/2026-11-03_fixes_source.md` (the document's text, item ids added). Spec: `docs/spec/Futran_Audit_Platform_Developer_Spec_v0.3.md` and the Build Schematic still bind.

## Global constraints (every workstream)

- Tenant from the session only; every endpoint calls `authorize`; audit log append-only; Python >= 3.11.
- Copy: plain professional English, sentence case, no filler. Field help uses the existing `FieldHelp` / `help` text pattern.
- **No new Python dependencies.** The user's laptop runs `alembic upgrade head` on start and never reinstalls packages. httpx, openpyxl, python-docx, pypdf, anthropic are available.
- **Migrations additive only** (new tables or nullable columns). Exactly one Alembic head: before pushing a migration, rebase on `origin/build/v1` and point `down_revision` at the current head.
- The user has real test data (a client called "test", 47 users, 8 departments, 8 AI systems, one engagement in progress). Nothing may change or delete existing rows on upgrade, except additive backfills that are clearly safe.
- Phone width 375 px: no sideways page scroll; touch targets 44 px.
- Push after every commit: `git fetch origin build/v1:refs/remotes/origin/build/v1 && git rebase origin/build/v1 && git push origin HEAD:build/v1`.
- Commit messages end with the two attribution lines given in the brief.

## Shared names

- `User.job_level` (String(30), nullable) — added by **P**. Values: `executive`, `department_head`, `manager`, `level_3`, `level_2`, `level_1` (labels "Executive", "Department head", "Manager", "Level 3", "Level 2", "Level 1"). R reads it for "Who uses it → by role level" and must tolerate it being null for every user.
- Wording: the platform's role names for people (Client Admin, CAICO, Department Lead …) are called **"AI compliance role"** wherever users see "Role" in the people screens, the user template and the register's governance roles. "Job title" is the person's own working title at their company.
- AI calls go only through `app/ai/client.py` (`client_for(app_state, settings)` → object with `complete(...)`). AI keeps this interface while adding providers; R's monthly model-list refresh uses it and must work when no AI is connected (then it only reminds the Futran Admin).

## Item notes and rulings

- **F1 "LLM of choice, connect AI".** A Futran Admin settings section chooses the provider (Anthropic Claude, OpenAI, Azure OpenAI, Google Gemini), model and API key; the key is stored encrypted with the existing token helper and never returned to the browser; "Test connection" makes one small call. Every AI feature (law refresh, Draft with Claude, litigation tracker, copilot, obligations, questionnaires) uses the connected provider. With nothing connected the current behaviour stays (env key, then the test-mode demonstration model). Non-Anthropic providers are called with httpx (no new packages) and are tested against mocked HTTP only; say so in the screen's help text. Ruling: one platform-wide connection, not per client.
- **F2 "Needed by".** Explain in a column header help icon and on the roles catalogue: the stage of the audit (or "before go-live") by which the role must be filled, and what happens if it is not.
- **F3 / F11 law library vs reference data.** Law library = the laws themselves (versions, requirements, scope tests). Reference data = the lists the platform uses around them (jurisdictions, catalogues, templates' lookups, law refresh runs). Put a short explanation at the top of each screen, link each to the other, and make a law row in reference data open the full law record page (its own screen) instead of the side table; keep a "pop out" link if the side panel stays.
- **F4 / C1 navigation.** Group the flat lists into menus. Futran: Home and work (role homes, Dashboard, Clients), Law library (Law library, Refresh and review, Roles and committees as its own entry, Obligations to review, Regulatory updates), Business (Litigation, Opportunities, Client alerts, Insights), Assurance (Trust Center confirmations, Client policy reviews, Platform trust), Administration (Users, Templates, Reference data, Email and groups, Email log with outbox, Audit log, Settings). Client: Home (role homes, Getting started, My tasks), Audit (Review, AI systems, Documents, Report, Responses, Remediation), AI governance (AI system register, AI inventory, Governance, Company roles, Policies, New AI projects, Regulatory updates, Add-ons), People and training (People, Attestation, My AI attestation, AI literacy training, My training), Data and integrations (Bias test data, Integrations, Monitoring, Customer questionnaires, API and webhooks, Trust Center), Email (Email connection, Groups, Email log). Menus show only entries the person can use; a group with one entry renders as a plain link; keyboard and phone friendly. Existing routes do not change.
- **F6 obligations flag.** A count badge on "Obligations to review" (and its group) for undecided obligations, for people who can approve them.
- **F10 templates.** Text inputs sized to their content; the "v1" chip removed; an (i) beside the template name shows revision number, approved date and who approved.
- **F12 add users.** An "Add user" button on the Futran Users screen using the existing invitation flow.
- **F13 audit log.** The "When" column wide enough for date and time without wrapping.
- **F14b outbox.** The email log gets an "Outbox (test mode)" tab showing the outbox; the old route redirects there; the Outbox nav entry goes.
- **F8 opportunity scan.** A Futran Admin setting "Look for new opportunities every N days" (7, 15, 30 or a custom number; off allowed). The daily job runs the scan when N days have passed since the last scan, and the Settings section shows the last and next run and a "Run now" button. The scan opens opportunities (through the existing `open_from_trigger`, once per client and reference) for: (a) laws added or changed in the law library since the last scan that apply to a client (scope engine), (b) regulatory updates published since the last scan that matched a client, (c) renewal audits — completed engagements whose anniversary falls within the next 90 days and that have no annual review started. Each records why now. The independence rule and Chief Auditor approval still apply.
- **C2 admin home.** Replace the "gave X the role of Y for Z" lines with a scrollable grid: name, AI compliance role, department, changed by, when. A person's row opens their history: every role and department change with who and when, from the audit log. Department changes are captured the same way (audit log rows already exist or are added).
- **C3 People ⋯ menu.** The menu shows the editable settings directly (Edit details, AI compliance role, Department, Job level, Resend invitation, Remove) instead of a single "Edit".
- **C4 heads of department from CSV.** The department upload accepts a "Head of department" column with a name or email; it is matched to an existing user (email first, then exact full name within the client); unmatched or ambiguous names are listed as warnings, never guessed.
- **C5 department workbook.** The department template is an XLSX workbook: a "Departments" sheet (name, parent, head of department, headcount) and one sheet per department for its users, with instructions and data validation. Upload accepts the workbook (all sheets) or a CSV; "Upload users to this department" on a department accepts a CSV or one sheet for that department; one file for everyone still works.
- **C6 user template.** Columns: Full name, Work email, Department, Job title (their working title at the company), Job level, AI compliance role. Old column names are still accepted on upload.
- **C7 register template.** The register CSV/XLSX template's columns match the fields the system needs, in the form's order, with required columns marked and allowed values listed.
- **C8 import from inventory.** Help text on the button: it copies tools and use cases the client declared in the engagement's AI inventory (stage 3) into the register.
- **C9 departments.** A tool used by several departments lets the user pick which ones.
- **C10 who uses it.** "By role level": choose job levels and/or AI compliance roles (and optionally job titles taken from the user list). "Named users": a searchable multi-select of the client's users with select all / clear, filterable by department; the user count is calculated from the selection.
- **C11 system owner.** The owner picker groups or sorts users by department.
- **C12 vendor and model.** A vendor → model catalogue (seeded with major vendors and their current models; editable by the Futran Admin in reference data). The model field is a dropdown for the chosen vendor with "Other", whose typed value is saved for that client's future picks. Monthly job: when AI is connected it proposes catalogue additions for the Futran Admin to accept; otherwise it reminds the Futran Admin to review the list. Nothing changes the catalogue without a person accepting.
- **C13 whose data.** Add "The company's own data".
- **C14 laws.** The system records where it runs (country, state, city) and where the people whose data it uses are (one or more places). Laws are suggested from the law library's scope engine using those places and the system's features — no AI. The user picks from a law library dropdown and can accept or remove suggestions; suggestions show the reason.
- **C15 governance roles.** Add a "Geography of law" column (the law's jurisdiction), and call the role column "AI compliance role".

## Review focus

1. Navigation: every route still reachable for every role that could reach it before; active state; phone width.
2. People imports: bad and partial files never half-apply; name matching never assigns the wrong head; old templates still import.
3. AI provider secrets never leave the server; a failed provider never breaks features that worked before.
4. Opportunity scan creates each opportunity once, respects independence, survives a failing client.
5. Register wizard: existing systems open and save unchanged; geography-based law suggestions match the scope engine.
